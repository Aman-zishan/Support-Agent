The Project

Same four specialists, two coordinators, one gate

A support desk with two ways to coordinate the same four specialists. The choice between them is the architectural decision this workshop is about.

Path A
Supervisor Agent
The model decides who handles the ticket. A fifth specialist is one more line; there is no router to edit.
new Agent({
  agents: { billing, technical,
          account },
  tools: { requestRefundApproval },
  delegation: { onDelegationStart }
})
Use when the path is not knowable up front.
Path B
Deterministic Workflow
The path is fixed in code. Every ticket passes the same guardrails in the same order, every run.
0
Validate: length, ID format, PII
1
Triage: classify and prioritise
2
Specialist: resolve or recommend
Use when compliance needs the same steps every run.
🔒
One Shared Gate
Both paths end at the same refund approval step. Exactly one place in the codebase can move money, and it always sits behind suspend().
// refund-approval.ts
if (amount <= LIMIT)
  await processRefund(…);
else if (!resumeData)
  await suspend({ … });
Over $50 pauses for a manager. Under it settles instantly. The number is configurable; the bound is the point.
Block 1 · Security Primitives

Least authority is a property of the tool list

🛡
Capability, not instruction

Telling billing "do not refund" is a request a hostile prompt can override. Leaving processRefund off its tool list is a fact one cannot. Enforce with the runtime, not with prose.

agents/triage.ts
export const triageAgent = new Agent({
  description: "Classifies a ticket … takes no action",
  model: () => supportModel(),
  // no `tools` property at all
});

agents/billing.ts
tools: { lookupCustomer, getOrderHistory }
// processRefund is not here. It is not a tool.
🔄
Reversibility & Idempotency

Split every irreversible action into recommend and execute, with a checkpoint between. Make execute safe to call twice.

✓billing recommends → gate decides → processRefund()
✗billing agent calls processRefund as a tool
✓retry returns the same refund ID, no second row
✗agent "remembers" to check for a previous refund
Block 1 · Security Primitives

Bound the damage, type the boundary

💥
Bound What Can Go Wrong

If the model hallucinates or is manipulated, the worst case per ticket is $50. Above that, a person decides. The number is policy; the bound is architecture.

workflows/refund-approval.ts
export const AUTO_APPROVE_LIMIT = 50;

if (refundAmount <= AUTO_APPROVE_LIMIT) {
  const result = await processRefund({
    orderId, amount: refundAmount, reason });
  return { action: "refund-auto-approved", … };
}
if (!resumeData) await suspend({ … });
// stops here until a manager calls resume()

Block 1 · Human-in-the-Loop

Autonomy is a policy value, not a vibe

Classify
Refund ≤ $50
Refund > $50
Delete account
Fully automated Always a human
Automate

Low cost of being wrong, easy to undo. Classification, lookups, drafting a reply. The agent runs end to end.

Pause

Cost scales with a number you can read: amount, row count, blast radius. suspend() parks the run; resume() continues it with the decision.

Never automate

Irreversible, or outward-facing with legal weight. Account deletion, external emails, contract terms. The agent drafts; a person acts.

The threshold moves as trust is earned. The shape of the gate does not: recommend, park, decide, execute.

Block 1 · Code Deep Dive

HITL: Suspend & Resume

workflows/refund-approval.ts — executeRefundApproval

async ({ inputData, resumeData, suspend }) => {
  const { refundAmount, orderId, reason } = inputData;

  if (!refundAmount || !orderId) return { action: "no-refund", … };

  if (refundAmount <= AUTO_APPROVE_LIMIT) {
    const r = await processRefund({ orderId, amount: refundAmount, reason });
    return { action: r.created ? "refund-auto-approved" : "refund-already-issued", … };
  }

  if (!resumeData) {  // first pass: no decision yet
     await suspend({
       message: `Refund of $${refundAmount} requires manager approval`,
       refundAmount, orderId, customerId, agentRecommendation: reason,
     });
   }

  // second pass: resume() re-enters here with resumeData set
  const { approved, managerNote } = resumeData;
  if (!approved) return { action: "refund-declined", managerNote, … };
  const r = await processRefund({ orderId, amount: refundAmount, reason, managerNote });
  return { action: "refund-approved", refundId: r.refundId, managerNote, … };
}
What actually happens
1Step runs; no resumeData
2suspend() snapshots the run to storage
3Worker is released. Process may exit.
4Hours later: resume({ approved })
5Same step re-executes, now with a decision
The step runs twice. Everything before the suspend check runs again on resume, so it must be side-effect free or idempotent. Ours is: the only write is behind the gate.
Shared by both paths. The support workflow wraps this function as a step. The supervisor reaches the same run through a non-blocking requestRefundApproval tool. One gate, two doors.
Block 1 · Defense in Depth

Guardrails: At the Door and Mid-Run

🛑
At the door: the validate step

Runs once, before any agent sees the ticket. Length and ID format via Zod; PIIDetector redacts card numbers and SSNs so specialists never see the raw text. LLM-based, so it catches what regex misses.

⚠
Why the injection detector is off

Disabled here on purpose. At threshold 0.7 on Groq's open-weight models it flagged legitimate refund requests as injection. A guard whose false-positive rate you haven't measured is not a control — it is an outage waiting for a customer. Measure it, then set the threshold.

⚡
Mid-run: reactive signals

Door guardrails cannot help on step 7 of an agent loop, when the model is about to promise a refund. A processor can inject policy during the run. Block 5.

workflows/support-workflow.ts

import { PromptInjectionDetector, PIIDetector }
  from "@mastra/core/processors";

new PromptInjectionDetector({
  model: () => supportModel(),
  detectionTypes: ["injection", "jailbreak", "system-override"],
  threshold: 0.7,
  strategy: "block",
  // models without native JSON-schema output:
  structuredOutputOptions: { jsonPromptInjection: true },
});

new PIIDetector({
  model: () => supportModel(),
  detectionTypes: ["ssn", "credit-card"],
  threshold: 0.6,
  strategy: "redact",
  redactionMethod: "mask",
});

// Both are built lazily and memoised: a missing API key
// must not stop Studio and the no-LLM demos from booting.
Block 1 · Scalability

Storage Is the Backbone, Not a Cache

One LibSQLStore backs four things at once. Every scaling property of this system falls out of that choice.

⏸
Suspended snapshots
A parked refund survives a restart, a deploy, or a day.
🧠
Memory per thread
Last 40 messages plus a working-memory template carrying the customer ID.
🔔
Signal inbox
Notifications for idle threads wait here. Only libSQL, Postgres and MongoDB support it.
🔎
Traces
Who delegated to whom, with what prompt. Studio reads them from the same file.
Suspend frees the worker
A suspended run holds no thread, no socket, no process. Ten thousand refunds waiting on managers cost you rows, not RAM. This is why HITL and horizontal scale are the same feature.
src/mastra/index.ts

const storage = new LibSQLStore({
  id: "support-agent-storage",
  url: "file:./support.db",
});

export const mastra = new Mastra({
  agents: { supportSupervisorAgent, triageAgent, … },
  workflows: { supportWorkflow, refundWorkflow },
  storage,
  observability: new Observability({
    configs: { default: {
      exporters: [new DefaultExporter()] } },
  }),
});
The one multi-instance trap
Signals are delivered through the store's pub/sub. With two nodes and no shared pub/sub (Redis), a signal sent on node A never reaches the run living on node B. It fails silently. This bites in staging, not locally.

Block 2 · Hands-On

Put the invariant in the store, not the prompt

"Never refund an order twice" can live in the instructions, in the tool code, or in a constraint. Only the constraint still holds when two workers race the same approval.

db/index.ts
CREATE TABLE refunds (
  id           TEXT PRIMARY KEY,
  order_id     TEXT NOT NULL UNIQUE REFERENCES orders(id),
   amount       REAL NOT NULL,
  manager_note TEXT,  -- who decided, and why
  created_at   TEXT NOT NULL
);

// Two files, two owners:
//  support.db      Mastra's: memory, runs, signals, traces
//  support-data.db  yours: customers, orders, refunds

export const getOrderHistoryTool = createTool({
  outputSchema: z.object({ orders: z.array(z.object({
    id, amount, date, status, item,
    alreadyRefunded: z.boolean(),  // or it recommends the same refund twice
   })) }),
  execute: async ({ customerId }) => /* real SELECTs */
});
🔄
Three layers, one that holds
Prompt: the tool reports alreadyRefunded, so a well-behaved model won't ask. Code: processRefund checks for an existing row. Store: UNIQUE makes the race unwinnable — the loser catches the constraint error, reads the winner's row, returns its ID.
// 3 concurrent processRefund() on ORD-3002

Still not a tool
processRefund() is a plain exported function. It is on no agent's tool list, so nothing a model outputs can reach it. Only the approval gate calls it, and it writes the refund row and the order status in one batch.
Block 3 · Native Multi-Agent

Supervisor & Subagents

Four agents behind an if/else is not a multi-agent system. It is one router with four functions.

Before: hand-rolled
tools/route-ticket.ts  (deleted)
const t = await triageAgent.generate(…);
const triage = JSON.parse(t.text);

if (triage.category === "billing")
  r = await billingAgent.generate(p);
else if (triage.category === "technical")
  r = await technicalAgent.generate(p);
else
  r = await accountAgent.generate(p);
Routing lives in TypeScript. A fifth specialist means editing the chain. Two specialists on one ticket is impossible.
After: native
agents/supervisor.ts
new Agent({
  id: "support-supervisor",
  agents: { billingAgent, technicalAgent,
     accountAgent },  // model routes directly
   tools: { lookupCustomer,
    requestRefundApproval },
   inputProcessors: [refundPolicyProcessor],
  memory: new Memory({ … }),
});
Mastra generates one agent-* tool per subagent, described by its description. The model routes — no triage classifier, because that would just be a second router. The refund gate is a non-blocking tool, not an inline workflow (next-but-one slide).
What you get for free
• Two specialists on one ticket
• Memory isolation per subagent
• Tool approvals bubble up the chain
• Traces showing who called whom
The catch
The description field is the routing logic now. A vague description is a routing bug, and it will not show up in your type checker.
Block 3 · Security

Delegation Hooks: Least Authority at the Boundary

Instructions are a request to the model. Hooks run in TypeScript; the supervisor cannot talk its way past them. Put the control where the model cannot reach it.

agents/supervisor.ts — defaultOptions.delegation
onDelegationStart: async (ctx) => {
  // runaway loop guard
  if (ctx.iteration > MAX_DELEGATIONS) return { proceed: false, rejectionReason: … };

  // no billing work without an identified customer
   if (ctx.primitiveId === "billing-agent"
     && !/\bC\d{3,}\b/.test(ctx.prompt))
     return { proceed: false, rejectionReason: "No valid customer ID …" };
   return { proceed: true };
},

onDelegationComplete: async (ctx) => {
  if (ctx.error) { ctx.bail(); return { feedback: "… escalate to a human" }; }
  if (ctx.result.finishReason === "tool-calls" && !ctx.result.text.trim())
    return { resultText: "… ran its tools but produced no answer" };
},

messageFilter: ({ messages }) =>
  messages.slice(-10).map(scrubCardAndSSN)
onDelegationStart
Fires before a subagent runs. Reject, rewrite the prompt, or cap its steps. It guards the specialist delegations; the refund path is a tool, so it enforces the same customer-ID check inside itself — least authority at whichever boundary the risk crosses.
onDelegationComplete
Fires after. Catches the nasty case: a subagent that stops on a tool-calls step returns empty text, which reads to the supervisor as a successful answer. resultText replaces it.
messageFilter
Subagents receive conversation history for context, including the card number pasted three turns ago. Trim and scrub before it leaves the supervisor.
Block 3 · Architecture

Supervisor or Workflow?

Not a style preference. Pick by who is allowed to decide the path: the model, or you.

🧠
Supervisor Agent
The model picks the path.
✓ Ticket could be any of four categories
✓ Might need two specialists, or none
✓ Conversational, multi-turn
✓ New specialists added often
Cost: two runs of the same ticket can take different paths. Harder to audit and to test.
🔗
Workflow
You fix the path in code.
✓ Every ticket must clear the same guardrails
✓ Regulators ask "what ran, in what order?"
✓ Steps must be retryable in isolation
✓ A step must survive a restart
Cost: every new branch is a code change and a deploy.
⚖
Where the approval goes
Put approval where the risk lives.
Risk is the tool call itself → requireApproval on the tool.
Risk is inside a step → workflow suspend(). ◀ ours
The supervisor reaches the gate through a non-blocking tool: it starts the run and returns at once. The $50 decision is in the workflow, never in the prompt — the model only decides to call, never to approve. And a suspended approval never freezes the chat.

Block 5 · Signals

When the Agent Has to Wait

The hole you just built
The $897 refund suspends and waits for a manager. Correct, and it leaves the customer conversation dead.
The manager approves twenty minutes later in an ops console. Nothing tells the customer, because the only way to make the agent speak is for the customer to speak first.
The actual cause
agent.stream() couples two things that are not the same:
  • who asked the question
  • who owns the response stream
Whoever called stream() gets the answer. Nobody else can see it, add to it, or trigger it.
What signals change
The thread becomes the shared object. Any number of clients subscribe to it; any of them can push context in; the agent can be woken by something that is not a user.
const sub = await agent.subscribeToThread(
  { threadId, resourceId });
for await (const chunk of sub.stream) { … }

// elsewhere, from a process that never asked anything:
await agent.sendNotificationSignal(
  { … }, { threadId, resourceId });
Requirements: the agent has Memory, the store supports the signal inbox (libSQL, Postgres, MongoDB), and you pass both threadId and resourceId.
⚠ experimental  Signals are @experimental in @mastra/core. Pin your version.
Block 5 · Signals

Four Ways Into a Running Thread

sendMessage()interrupt
The active run sees it now. The customer correcting themselves mid-answer.
agent.sendMessage({
  contents: "Actually it's ORD-1002",
  attributes: { name: "Alice", sentFrom: "web-chat" }
}, thread)
The model sees <user name="Alice" sentFrom="web-chat">…</user>. Attributes are how it knows who is talking.
queueMessage()wait
Let the current turn finish, then start a new run. Useful context that is not urgent.
agent.queueMessage({
  contents: "Internal: comped this one last month.",
  attributes: { name: "Rep-Jordan", sentFrom: "internal-console" }
}, thread)
A human rep adding context the customer never sees.
sendNotificationSignal()external event
Something outside the conversation happened. Wakes an idle thread, or banks the event for later.
agent.sendNotificationSignal({
  source: "ops-console", kind: "refund-approved",
  priority: "high", dedupeKey: `refund:${refundId}`,
}, { threadId, resourceId, ifIdle: { behavior: "wake" } })
dedupeKey collapses the manager's double-click. ifIdle: 'persist' stores it silently instead of waking.
reactivemid-run guardrail
A processor watches each step and injects guidance the moment a condition holds.
processors/refund-policy.ts
async processInputStep({ messageList, sendSignal }) {
  if (REFUND_TRIGGER.test(recentText))
    await sendSignal({ type: "reactive", contents: POLICY, transient: true });
}
transient means delivered this turn, never stored. One fresh copy each step, not ten stale ones in history.
Block 5 · Live Demo

Closing the HITL Loop

The refund gate and the conversation were two disconnected systems. One signal joins them.

1
Customer asks for the $897 refund
Supervisor delegates to billing, then calls requestRefundApproval
↓
2
Run suspend()s; tool returns pending
Snapshot to storage. The supervisor tells the customer & ends its turn — the chat stays open
↓
3
Thread goes idle. Nobody is typing.
The process could exit here entirely
↓
4
Manager approves → resume()
Real refund row written, real refund ID minted
↓
5
sendNotificationSignal() wakes the thread
The agent tells the customer. No user prompt behind it.
npm run signal:approval
// after resume() returns a REAL refundId
await agent.sendNotificationSignal({
  source: "ops-console", kind: "refund-approved",
  priority: "high",
  summary: `Refund ${refundId} approved by manager`,
  dedupeKey: `refund:${refundId}`,
}, { threadId, resourceId, ifIdle: { behavior: "wake" } });
Why this matters
Every HITL system has this gap. The approval lands somewhere the conversation cannot see, and someone writes a cron job to poll for it. This is the same thing without the cron job, and it survives the process dying because the thread lives in storage.
Then npm run signal:multiplayer: an observer that never asked anything, a mid-run interrupt, a queued internal note. Three clients, one thread, one history.
